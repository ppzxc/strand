# `stream_id`는 64비트로 두고 헤더를 20바이트로 늘린다

`stream_id`는 `1`~`2^63-1`이고 최상위 비트는 늘 0이다. 홀짝 번호 공간, 단조 증가, 번호 역행 연결 오류, `highest_peer_stream_id`는 0.1.0 그대로다. 필드 순서도 그대로이고 `stream_id`만 4바이트에서 8바이트로 늘어 헤더가 20바이트가 된다. 프레임마다 붙는 와이어 형식이라 한 번 퍼지면 되돌리기 어려워 결정을 남긴다. 규칙 자체는 규격이 정한다.

## 왜 늘렸나

0.1.0의 31비트 번호는 HTTP/2와 같은 구조라서 번호를 다 쓰면 연결을 끝내야 했다. 이것은 "프로토콜은 내부 사유로 연결을 끝내지 않는다"([ADR 0004](0004-장기-연결-안정성-포지션.md))와 부딪힌다. 64비트면 번호 공간마다 2^62개이고, 초당 10억 요청이어도 약 146년이 걸린다.

소진 규칙(다음 번호가 경계를 넘으면 그 요청을 로컬에서 실패시키고 `CLOSE(NO_ERROR)`)은 경계만 바꿔 남긴다. 닿지 않는 경계라도 같은 입력에 규격의 답이 하나여야 하고, 로컬 실패만 내고 연결을 남기면 그 뒤 모든 요청이 실패하는 연결이 된다.

## Considered Options

- **번호 순환**(SMPP, MQTT, AMQP): 늦게 온 프레임이 같은 번호의 새 스트림에 붙을 위험이 있다. 그 위험 구간은 "상대가 CANCEL을 처리할 때까지"라서 번호 개수로 막을 수 없고, 막으려면 CANCEL 확인 같은 새 장치가 필요하다. 이것은 "RESET에는 RESET으로 답하지 않는다"와 부딪힌다. 번호 역행 판정, `highest_peer_stream_id`, CLOSE의 `last_stream_id`도 모두 단조 증가에 기댄다.
- **48비트**(`reserved`를 흡수해 16바이트 헤더 유지): 번호 공간마다 2^46개라 초당 100만 요청이면 약 2년 만에 바닥난다. "사실상 소진되지 않는다"고 할 수 없다.
- **QUIC식 62비트 가변 길이 정수**: 번호 공간을 키운다는 발상만 가져온다. 가변 길이는 고정 헤더를 깨고, 단방향 스트림은 결과 확정성과 맞지 않는다.

## Consequences

- 프레임마다 4바이트가 늘어난다. payload가 100~200바이트인 문자 메시지에서 2~3%다. 우선순위가 안정성 > 성능이므로 받아들인다.
- `length` 최솟값이 16, 가장 작은 프레임이 20바이트가 된다. `reserved` 2바이트는 확장할 자리와 4바이트 정렬을 위해 남긴다.
- 최상위 비트가 0이라 Java 8의 부호 있는 `long`으로 바로 비교할 수 있다. 적합성 벡터는 2^53을 넘는 값을 JSON 숫자로 정확히 나타낼 수 없는 언어를 위해 번호를 10진수 문자열로 쓴다.
- 방향 비트는 두지 않는다. 서버발 알림은 서버 개시 요청과 그 응답으로 나타낸다.

근거: [번호 소진 제거 방식](https://github.com/ppzxc/strand/issues/148).
