# Strand는 서버 사이에서 오래 유지되는 단일 연결의 뼈대다

Strand는 금융 거래, 문자 전송처럼 **극단적인 안정성 위에 성능까지 필요한 서버 사이(B2B) 통신**을 위해, 연결 하나를 오래 안정적으로 유지하며 요청 하나에 응답 하나를 다중화하는 프로토콜이다. 규격 0.1.0은 "SIMPLE IS BEST"를 최우선으로 두었고([#76](https://github.com/ppzxc/strand/issues/76)), 그 결과 번호 소진으로 연결이 끝나고 연결이 끝날 때 대기 중이던 요청은 모두 "결과 모름"이 됐다. 이 결정은 우선순위를 다시 세우고, 프로토콜이 보장하는 것과 애플리케이션에 맡기는 것의 경계를 정한다. 규칙 자체는 규격 0.2.0이 정한다.

## 우선순위

**안정성 > 성능 > 단순성.** 단순성은 같은 보장을 주는 방법 가운데 하나를 고르는 기준이다. 그래서 #76에서 단순성을 이유로 뺀 CLOSE의 `last_stream_id`를 되살렸다([처리 안 됨 확정 범위 넓히기](https://github.com/ppzxc/strand/issues/155)). 보장에 기여하지 않는 것(유예 상태, `STREAM_CLOSED`)은 되살리지 않았다.

## 원칙: 프로토콜은 내부 사유로 연결을 끝내지 않는다

연결이 끝나는 사유는 상대의 규칙 위반, 무응답, 과도한 사용, 인증 실패·폐기, 애플리케이션의 판단뿐이다. 이 원칙에서 다음이 나왔다.

- `stream_id`를 64비트로 늘려 번호 소진을 실제 운영 범위 밖으로 밀어냈다([ADR 0005](0005-64비트-stream-id.md)).
- 생존 확인 주기를 협상하지 않는다. 값이 맞지 않아 연결을 거절할 일이 없다([장기 연결 생존성](https://github.com/ppzxc/strand/issues/151)).
- 자기 과부하는 연결을 끝낼 사유가 아니고, 요청 단위 거절(`RESET(REFUSED)`)로 나타낸다([과부하 제어](https://github.com/ppzxc/strand/issues/152)).

## 프로토콜이 보장하는 것

1. **결과 확정성**: 보낸 요청마다 로컬 결과를 정확히 하나 내고, 그 결과가 **응답 받음 / 처리 안 됨 / 결과 모름** 중 무엇인지 알린다. "처리 안 됨"으로 확정할 수 있는 경우를 넓히는 것이 프로토콜의 책임이다(CLOSE의 `last_stream_id`, 전송 계층에 넘기지 못한 요청, 끊기 전 `REFUSED` 돌려보내기)([결과 확정 메커니즘](https://github.com/ppzxc/strand/issues/150)).
2. **장애 감지**: 유휴 PING, 확인 대기, 요청 기한의 메커니즘을 규격에 두고, 값은 로컬 설정으로 둔다. 줄 앞 막힘이 막는 시간은 `max_frame_size` 상한(1 MiB) 프레임 하나로 묶는다([큰 메시지와 줄 앞 막힘](https://github.com/ppzxc/strand/issues/156)).
3. **연결 인증**: 연결을 맺을 때 `AUTH` 관문을 한 번 지나야 애플리케이션 프레임을 주고받는다. 채널은 기밀성·무결성·서버 인증을 조건 없이 갖춰야 한다([인증 위치](https://github.com/ppzxc/strand/issues/153)). payload로 로그인하면 다중화 때문에 로그인 응답 전에 다른 요청이 도착할 수 있고, 중복 판단이 기대는 "인증된 상대"를 하나로 정할 수 없다.

## 애플리케이션에 맡기는 것

- **"결과 모름"을 닫는 일과 중복 처리 0**: 같은 요청인지는 **인증된 상대 + `idempotency-key`**로 애플리케이션이 판단한다. 프로토콜은 키를 나르기만 한다. 프로토콜이 중복을 직접 판단하는 사례(MQTT QoS 2, AMQP, Kafka idempotent producer)는 모두 세션 범위에 한정되는데, Strand에는 연결을 넘는 세션이 없고 재전송은 다른 서버 인스턴스에 닿을 수 있다.
- **순서 보장**(같은 키의 요청 순서), **우선순위**(우선순위마다 연결을 나눈다).
- **무중단 연결 교체**(make-before-break): 클라이언트 연결 관리의 몫이다.
- **큰 데이터**: 상한보다 큰 데이터는 대역 외로 보내고 Strand로는 참조만 보낸다.

## 연결을 넘는 세션은 없다

연결을 넘는 세션(영속 시퀀스, 재접속 동기화, 세션 계층 재전송)은 두지 않는다. 연결이 끝나면 프로토콜 상태는 모두 사라지고, 재접속은 언제나 새 연결이다. 요청 하나에 응답 하나인 모델에서는 응답이 없다는 것이 이미 유실 신호라서 시퀀스 간격 감지가 할 일이 없고, 세션 재전송을 넣어도 애플리케이션 중복 판단은 그대로 남는다([연결을 넘는 세션 도입 여부](https://github.com/ppzxc/strand/issues/149)).

## 성능

성능은 구현의 몫이다. 규격은 고정 헤더, 다중화, 협상된 한도로 성능을 **막지 않는 데서** 그치고, 압축이나 우선순위 같은 성능 기법을 요구하지 않는다.

## 사용 환경과 범위

- strand over TCP 하나만 둔다. 대상이 서버 사이 통신이라 strand over WebSocket은 공식 사용 환경에서 뺀다. 서버 개시 요청(양방향)은 유지한다.
- 애플리케이션 payload는 불투명 바이트열이다. Protocol Buffers 대응은 비규범 매핑으로 내린다. 프로토콜은 payload를 해석하지 않으므로 형식을 강제할 수 없고, ISO 8583이나 SMPP PDU를 그대로 싣는 게이트웨이를 막지 않는다.
- 스트리밍, 단편화, 프레임 무결성 검사(TLS가 맡는다), 송신 시각, 압축은 두지 않는다.
- 0.1.0과 와이어 호환을 지키지 않는다. 연결 서문의 `STR0`은 유지한다.

## Considered Options

- **"SIMPLE IS BEST" 유지**(0.1.0): 규칙은 가장 적지만, 대상 도메인에서는 결과 모름 하나하나가 대사·보상 거래 비용이 된다.
- **연결을 넘는 세션**(FIX식 영속 시퀀스와 재전송): 결과 모름을 프로토콜이 줄일 수 있지만, 영속 저장소와 인스턴스 고정이라는 새 장애 지점이 생기고 애플리케이션 중복 판단은 여전히 남는다.
- **채널(mTLS)에만 인증을 맡김**: 규격은 단순해지지만, TLS를 끝내는 중간 장비가 있으면 신원이 끊기고 bearer 토큰 같은 자격 증명을 실을 곳이 없다. 비교한 금융·문자 전송 프로토콜(SMPP, FIX, MQTT, AMQP, ISO 8583 환경)은 모두 프로토콜 안에 인증 관문을 둔다([금융·문자 전송 프로토콜의 신뢰성 메커니즘 비교](https://github.com/ppzxc/strand/issues/147)).

## Consequences

- 와이어 형식이 0.1.0과 호환되지 않는다(헤더 20바이트, CLOSE payload, `AUTH`). 구현과 적합성 벡터(형식 2)를 함께 고친다.
- "중복 처리 0"을 원하는 애플리케이션은 `idempotency-key`를 저장하는 공유 저장소를 직접 갖춰야 한다. 규격은 권고 패턴만 비규범으로 준다.
