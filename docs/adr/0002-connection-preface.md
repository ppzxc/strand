# 연결 서문은 8바이트 바이너리 값으로 둔다

클라이언트는 연결 직후 8바이트 연결 서문 `C0 DE 53 54 52 30 00 00`을 한 번 보낸다. 서문은 프레임 파서에 들어가기 전에 엉뚱한 상대를 걸러내고 메이저 버전을 확정한다. 이 바이트는 한 번 퍼지면 바꾸기 어렵고, 맥락 없이는 왜 이런 값인지 알기 어려워 결정을 남긴다. 규칙 자체는 규격이 정한다.

## 바이트 구성

| 바이트 | 값 | 이유 |
| --- | --- | --- |
| 0~1 | `C0 DE` | 첫 바이트 `0xC0`은 최상위 비트가 1이라 ASCII 인쇄 문자(`0x20`~`0x7E`)로 시작하는 HTTP, Redis, SMTP 같은 텍스트 프로토콜 요청과 첫 바이트에서 구분된다. 다른 바이너리 프로토콜과는 앞 6바이트 전체를 비교해 구분한다. |
| 2~5 | `53 54 52 30` (`"STR0"`) | 헥스 덤프에서 프로토콜 이름과 메이저 버전 0을 사람이 바로 읽는다. |
| 6~7 | `00 00` | 예약 영역. 전체를 8바이트로 맞추고, 받는 쪽은 이 두 바이트를 검사하지 않는다. |

## Considered Options

- HTTP/2식 텍스트 서문(`PRI * HTTP/2.0\r\n\r\nSM\r\n\r\n`, 24바이트) [RFC 9113](https://www.rfc-editor.org/rfc/rfc9113): 낡은 HTTP/1.1 서버나 프록시가 이 연결을 오류로 끊게 하려는 장치다. 그런 상대를 고려할 필요가 없는 Strand에는 길고 불필요하다.
- 프레임마다 싣는 매직(Dubbo의 `0xDA 0xBB`, SOFABolt의 프로토콜 코드 1바이트): 연결 동안 바뀌지 않는 값을 모든 프레임에 반복한다. 프레임 헤더에서 식별값을 빼고 연결에서 한 번만 확인하는 쪽이 낫다.
- 첫 프레임에 통합(RSocket의 `SETUP`에 든 버전): 첫 제어 프레임을 읽어야 비로소 버전을 안다. 서문은 프레임 파서보다 앞에서 버전을 확정하므로, 지원하지 않는 상대에게 버퍼와 상태를 할당하기 전에 끊을 수 있다.
