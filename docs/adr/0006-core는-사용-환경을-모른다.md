# core는 사용 환경을 모른다

`strand-core`는 바이트를 파싱하는 상태 기계이고, 그 바이트가 TCP 스트림에서 왔는지 WebSocket 메시지에서 왔는지 모른다. 입력은 둘뿐이다. 어디서 잘라도 되는 **스트림 입력**과, 정확히 한 단위(서문 또는 프레임 하나)라고 주장하는 **단위 입력**이다. 바이트로 넘길 수 없는 입력(예: WebSocket 텍스트 메시지)은 "받았다"는 신호 하나로 알리며, 반응은 크기가 어긋난 단위 입력과 같다. WebSocket에만 있는 일(텍스트 구분, 메시지 조각 모으기, WebSocket Close)은 전송 모듈이 한다. 이 경계가 core 안쪽 구조(입력 자르기, 출력 진행, 구동 방식)를 정하고, 나중에 되돌리기 어려우며 코드만 봐서는 왜 비어 있는지 알기 어려워 결정을 남긴다. 규칙 자체는 규격이 정한다.

## 결정

- core의 타입, 메서드, 설정, 출력 어디에도 WebSocket이라는 개념이 없다. 엔드포인트 설정에 WebSocket 여부가 없고, 입력·출력·종료 경로가 환경으로 갈리지 않는다.
- 단위 입력의 경계 위반은 연결 단계에 맞게 core가 반응한다: 서문 단계와, 첫 프레임의 헤더를 읽을 수 없거나 HELLO가 아닌 경우는 아무것도 보내지 않고 닫고, 그 밖(유효한 HELLO 헤더에 크기만 어긋난 경우 포함)은 연결 오류이며, `type`이 CLOSE이면 CLOSE 없이 닫는다(규격 3.5절, 5.1절).
- 메시지를 조각으로 받아 모으는 일은 전송 모듈이 한다. 모을 크기의 상한은 core가 알린 `max_frame_size`다.
- 메시지 통로가 메시지 전체를 넘겼을 때는 바이트 스트림과 같은 진행 보고에 전체 길이를 준다. 통로가 닫히면 바이트 스트림과 같은 끊김 입력을 준다.
- core가 내는 출력은 프레임 하나를 실은 바이트뿐이다. WebSocket Close 1000은 전송 모듈이 낸다: 전송 종료 지시가 "남은 출력 뒤 닫기"이고 종료 원인이 `NO_ERROR` 연결 종료이면 남은 출력을 다 보낸 뒤 1000으로 닫는다.

## 맥락

설계 의도는 처음부터 "core는 바이트를 파싱할 뿐 TCP인지 WebSocket인지 모른다"였다. 그런데 구현은 엔드포인트 설정의 WebSocket 여부로 입력, 출력, 종료 경로를 갈랐고, WebSocket 메시지 종류, 메시지 조각 조립, 메시지 접수 보고, WebSocket 닫힘 입력, WebSocket Close 출력이 core에 있었다. 이 가운데 조각 조립과 접수 보고, 닫힘 입력은 core 테스트 말고는 쓰는 곳이 없었다. 제품 전송 모듈 가운데 WebSocket을 쓰는 곳이 아직 없어서 지금이 가장 싸게 걷어낼 때다. 규격이 정하는 사용 환경은 TCP와 WebSocket 둘이지만(규격 1.2절), 환경이 하나 더 생겨도 core를 고치지 않는 것이 목표다.

## Considered Options

- **core가 WebSocket 모드를 계속 안다**: 환경이 늘 때마다 core의 입력·출력·종료 경로에 분기가 늘고, 분기마다 core 테스트가 필요하다. 쓰는 곳 없는 메시지 조립과 접수 보고도 core가 떠안는다.
- **전송 모듈이 메시지를 바이트로 바꿔 스트림 입력으로만 넣는다**: 입력이 하나로 줄지만, 메시지 경계를 어기는 입력(한 메시지에 프레임이 둘이거나 반 개)을 core가 알 수 없어 전송 모듈마다 경계 위반 반응을 다시 구현하게 된다. 경계 위반을 core가 한 곳에서 처리하려고 단위 입력을 따로 둔다.

## Consequences

- 새 통로(환경)를 붙일 때 core를 고치지 않는다. 전송 모듈이 스트림 입력과 단위 입력 가운데 맞는 쪽을 고른다.
- WebSocket에서만 확인되던 요구사항(1000으로 닫기, CLOSE 송신 뒤 닫기, 텍스트 메시지)은 core 벡터로는 확인할 수 없고, 전송 모듈의 몫이므로 예제의 WebSocket 통로 테스트와 적합성 벡터의 전송 모듈 판단으로 확인한다.
- core 테스트는 단위 입력으로 메시지 통로의 경계 위반 반응을 확인한다.
