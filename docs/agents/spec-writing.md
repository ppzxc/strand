# 규격 작성 규칙

`docs/specification/STRAND_SPECIFICATION.md`를 고칠 때 따르는 규칙이다. 구현자는 규격만 읽고 구현할 수 있어야 한다.

## 규칙

- **규칙은 한 절에서만 정의한다.** 다른 곳에서 필요하면 절 번호로 가리킨다. 다시 적는 자리에는 대문자 키워드를 쓰지 않는다. 대문자 키워드(MUST, MUST NOT, SHOULD, SHOULD NOT, MAY)는 괄호 안에 쓰고, 열거를 이끄는 줄은 `(모두 MUST)`처럼 `모두`로 시작하는 괄호로 쓴다.
- **설계 근거는 본문에 두지 않는다.** "왜 이렇게 했나"는 이슈와 git 기록, 결정이 어렵고 맥락 없이는 의아한 것은 `docs/adr/`에 둔다. 구현자의 실수를 막는 안내는 근거가 아니라 `> 비규범 주석`으로 쓴다.
- **인용하지 않는 각주는 두지 않는다.** 본문을 고쳐 각주를 인용하는 곳이 없어지면 7절의 정의도 함께 지운다.
- **확장 기능은 양쪽이 기능 비트를 켠 연결에서만 쓴다.** 이전 버전이 모르고 지나치면 잘못 동작하는 기능이 대상이다. 모르는 항목을 건너뛰어도 되는 확장 영역의 선택 항목(2.4절)은 해당하지 않는다.
- **용어 정의의 정본은 규격 1.3절이다.**

## 각주 표기법

인용은 GFM 표준 각주 표기법을 쓴다. 본문에서는 영문 식별자 태그로 인용하고(예: `[^RFC2119]`), 정의는 7절에 모은다(예: `[^RFC2119]: RFC 2119, ...`). 태그는 IETF RFC의 관례를 따라 `RFC` 뒤에 번호를 붙이거나 대문자와 하이픈으로 쓴다.

7절에는 구현할 때 반드시 필요한 규범 참조만 둔다. 이 규격이 규범으로 인용하는 문서를 말한다. 설계할 때 참고하거나 비교한 문서는 두지 않는다.

## 벡터와의 대응

요구사항은 대문자 키워드 하나(MUST·MUST NOT·SHOULD·SHOULD NOT)가 정하는 행동이다(GLOSSARY.md "요구사항"). 정의한 자리마다 빈 앵커 `<a id="req-…"></a>`로 **요구사항 식별자**를 둔다. 식별자는 서술형 kebab-case이고 첫 단어는 영역(`hello-`, `auth-`, `close-` 등)이다. 보내는 쪽과 받는 쪽을 함께 정했으면 `-send`·`-recv` 앵커를 나란히 둔다. 패턴은 `^req-[a-z0-9]+(-[a-z0-9]+)*$`이다.

### 앵커 규칙

- 앵커는 키워드 괄호 바로 뒤에 둔다. 표 셀에서는 반응 문구 바로 뒤에 둔다. 키워드 괄호마다 앵커가 하나 이상 있어야 한다.
- 열거를 이끄는 줄은 `(모두 …)` 괄호로 표시하고 그 뒤에는 앵커를 두지 않는다. 대신 이어지는 목록의 최상위 항목과 표의 행마다 앵커를 둔다.
- 앵커의 키워드는 괄호 바로 뒤이면 그 괄호의 키워드다. 열거 항목의 앵커는 항목 안 자기 키워드 괄호가 있으면 그 키워드, 없으면 이끄는 줄의 키워드를 물려받는다. 5.1절 표의 행 앵커는 MUST다.
- 이 두 자리 밖의 앵커(고아 앵커)와 괄호 밖의 대문자 키워드는 허용하지 않는다. 같은 식별자를 두 번 쓸 수 없다.
- 다른 절을 가리키며 같은 요구사항을 다시 적은 줄에는 키워드를 쓰지 않고 앵커도 두지 않는다. 5.1절 연결 오류 목록처럼 다른 절의 요구사항을 모은 색인에도 앵커를 두지 않는다. 5.1절에서만 정의하는 항목과 표의 검사 순서·반응에는 둔다.
- 키워드 없이 서술했지만 벡터가 확인해야 하는 행동은 키워드와 앵커를 붙여 요구사항으로 만든다.

### 식별자를 바꾸고 지우는 규칙

- 문구만 다듬거나 문장을 다른 절로 옮길 때는 식별자를 그대로 두고 앵커를 문장과 함께 옮긴다.
- 관측할 수 있는 행동(값·반응·오류 코드)이 바뀌거나 요구사항이 나뉘거나 합쳐지면 옛 식별자를 지우고 새 이름을 쓴다. 그러면 옛 의미를 단언하던 벡터가 식별자 실재 검사에서 실패해 다시 검토된다.
- 의미가 같아도 더 나은 이름으로 바꿀 수 있다. 대신 옛 이름은 삭제 목록에 올린다.
- 지운 식별자는 `strand-conformance/src/test/resources/deleted-requirement-ids.txt`에 사유와 이슈 번호를 `#` 주석으로 적고 한 줄에 이름 하나를 적는다. 지운 이름은 규격 앵커, 벡터의 `requirements`, 제외 목록 어디에도 다시 쓰지 않는다.

### 벡터와 제외 목록

- 모든 벡터는 `requirements`에 자기 기대 결과가 단언하는 요구사항 식별자를 적는다. SHOULD·SHOULD NOT 요구사항은 적지 않으며 적으면 실패한다. 형식은 `docs/specification/STRAND_CONFORMANCE_VECTORS.md` 3절이 정한다.
- MUST·MUST NOT 요구사항은 그것을 가리키는 벡터가 있거나 `strand-conformance/src/test/resources/uncovered-requirements.txt`에 올라 있어야 한다. 줄은 `req-… 범주 사유`이고 범주는 둘뿐이다.
  - `관측불가`: 엔드포인트의 입출력(바이트와 메시지)으로 볼 수 없다. 예: TLS 요구, WebSocket 핸드셰이크 헤더.
  - `형식미지원`: 규격상 볼 수 있어야 하는데 지금 벡터 형식에 입력(트리거 단계)·비교 필드·이벤트가 없다. 형식(과 필요하면 규격)을 넓혀 갚을 빚이며, 갚으면 그 줄을 지운다.
- 제외 목록에는 MUST·MUST NOT만 올린다. 벡터가 가리키기 시작한 식별자는 줄을 지운다.

### `check`가 강제하는 것

`./gradlew check`의 `SpecCoverageTest`와 관련 테스트는 다음 가운데 하나라도 어긋나면 실패한다.

- 키워드 괄호와 `(모두 …)` 열거의 항목·행마다 앵커가 있다. 고아 앵커, 괄호 밖 키워드, 중복 앵커가 없다.
- 모든 벡터에 비어 있지 않은 `requirements`가 있고 `spec` 필드는 없다(스키마와 로더가 거부한다).
- 벡터가 가리키는 식별자가 규격에 실재하고 SHOULD·SHOULD NOT이 아니다.
- MUST·MUST NOT 요구사항마다 그것을 가리키는 벡터가 있거나 제외 목록에 있다.
- 제외 목록의 식별자는 규격에 실재하고, MUST·MUST NOT이며, 어떤 벡터도 가리키지 않고, 범주 표지가 있다.
- 삭제 목록의 이름이 규격 앵커, 벡터, 제외 목록에 나오지 않는다.
