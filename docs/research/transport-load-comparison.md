# nio·netty 전송 부하 비교: 하네스 검증과 첫 측정 해석

측정일: 2026-11-24. 하네스는 [`strand-load`](../../strand-load/README.md)(#422, 스펙 #430)이고, 이 비교가 필요한 이유는 [Netty 도입 적합성](netty-adoption.md)의 "도입 전 검증" 3번이다. 결과 JSON은 저장소에 커밋하지 않으며(머신 종속 수치) 이 문서에는 해석과 재현 조건만 남긴다.

## 결론

- **이 문서의 첫 측정은 전송 선택의 근거로 쓸 수 없다.** 측정 머신이 다른 작업과 코어를 나눠 써서(측정 중 load average 11~16, 코어 4개) 지연 꼬리와 처리량이 실행마다 크게 흔들렸다. 아래 행렬 표는 하네스가 끝까지 도는지 보인 것이지 nio와 netty의 우열이 아니다. 근거로 쓸 수치는 전용 머신에서 기본 설정(워밍업 30초, 측정 60초, 3회 반복)으로 다시 재야 한다.
- 이 측정으로 **믿을 수 있는 것**은 하네스 자체의 성질과 타이머로 정해지는 항목이다: 두 전송에 같은 TLS 조건이 걸리는지, 같은 JSON 스키마로 결과가 나오는지, 읽지 않는 상대가 기존 타이머로 끊기는지.
- 합격선은 상대 기준(nio 대비 netty)만 둔다. 절대 수치(허용 p99, 메모리 상한)는 실사용 조건이 정해진 뒤 별도로 정한다(스펙 #430 범위 밖).

## 측정 조건

| 항목 | 값 |
|---|---|
| 머신 | 4코어 aarch64, Linux 5.14, 서버·부하 생성기·다른 작업이 코어를 공유 |
| JDK | OpenJDK 25.0.4.1 (서버·부하 생성기 모두 같은 JVM) |
| netty | 4.1.101.Final, 서버 이벤트 루프 스레드 2개(독립 실행) |
| TLS | 1.3, `TLS_AES_128_GCM_SHA256`, JDK 기본 provider. 협상 결과가 JSON에 기록되어 두 전송이 같음을 확인했다 |
| 핵심 행렬 | 연결 {1, 100} × 본문 {64B, 1KiB} × {nio, netty} × TLS 켬 (8셀) |
| 시간(단축) | 워밍업 3초, 측정 8초, 3회 반복. **스펙 기본(30초/60초/3회)보다 훨씬 짧다** |

## 핵심 행렬 단축 실행 결과(참고용)

폐쇄형 포화 처리량 중앙값(요청/초)과 [최소–최대]:

| 연결 | 본문 | nio | netty |
|---|---|---|---|
| 1 | 64B | 26245 [24171–29812] | 28224 [26979–32818] |
| 1 | 1KiB | 25778 [24086–29078] | 22692 [18337–26370] |
| 100 | 64B | 15921 [15483–16785] | 29943 [25228–35929] |
| 100 | 1KiB | 15263 [14474–16354] | 22578 [21503–28665] |

읽을 때의 주의:

- 반복 사이의 범위가 중앙값의 20~40%에 이른다. 연결 1에서 두 전송의 차이는 이 범위 안에 있어 구분되지 않는다.
- 연결 100에서 netty가 nio의 약 1.5~1.9배로 나왔다. 방향은 "이벤트 루프를 연결이 공유하는 쪽이 연결 수가 많을 때 유리하다"는 가설과 맞지만, 한 번의 단축 실행이고 서버 스레드 모델이 다르다(netty 이벤트 루프 2개). 같은 가설이 전용 머신의 기본 설정 실행에서도 나오는지 확인하기 전에는 결론이 아니다.
- **개방형 지연 수치(50%·80% 도착률)는 버린다.** 많은 반복에서 `loadgenBottleneck`이 true였고(한 스케줄러 스레드가 예정 시각을 지키지 못함), 연결 100의 일부 셀은 부하 생성기가 일정을 포기해 측정 구간이 비었다. 부하 생성기와 서버가 코어를 다툰 결과이며 서버 한계가 아니다. 이 판정 표시(`loadgenBottleneck`)가 바로 이런 실행을 걸러내려고 둔 것이다.
- 연결 1·본문 1KiB 셀의 `errors`가 크게 나온 것도 개방형 구간에서 일정을 못 지킨 뒤 밀린 요청이 한도에 걸린 영향으로 보이며, 폐쇄형 구간(오류 0)과 구분해서 읽어야 한다. 전용 머신에서 다시 잰 뒤 남는 오류만 해석한다.

## 하네스 검증으로 확인한 것

### 개방형 지연이 서버 지연을 반영한다

서버에 100ms 지연을 일부러 넣은 개방형 실행에서 예정 시각 기준 지연의 p99가 95ms 이상으로 나온다(하네스 자체 시험). 요청을 보낸 시각이 아니라 예정 시각에서 재므로 서버가 느려도 지연이 축소되지 않는다(coordinated omission 방지).

### 측정 도구가 측정을 방해하지 않게 했다

첫 실행에서 측정 구간 시작의 자원 표본(JMX 초기화)과 히스토그램 첫 기록이 개방형 스케줄러를 수십~백 ms 멈춰 지연 p99를 부풀리는 결함이 드러났다. 부하 전에 표본 도구와 히스토그램을 미리 데워 해결했다. 이는 측정기가 측정 대상이 되는 전형적 사례라, 지연 비교에서는 항상 `sendLagP99Micros`와 `loadgenBottleneck`을 먼저 본다.

### 쓰기 정체: 읽지 않는 상대는 기존 타이머로 끊긴다(ADR 0004)

서버가 큰 요청을 계속 밀어 넣는 연결에서 상대 프로세스를 `SIGSTOP`으로 멈춰 읽지 않게 한 뒤 기본 설정(유휴 PING 30초, 확인 대기 5초)으로 측정했다.

| 전송 | 감지까지(ms) | 끊김 | 서버 RSS 증가 |
|---|---|---|---|
| nio | 40139 | `ERROR_CLOSE`, 오류 코드 6(`UNRESPONSIVE`), 로컬 송신 | 약 1.3MB |
| netty | 40149 | `ERROR_CLOSE`, 오류 코드 6(`UNRESPONSIVE`), 로컬 송신 | 약 1.6MB |

- 두 전송 모두 새 타이머 없이 기존 확인 대기(`UNRESPONSIVE`)로 끊겼고 감지 시간이 같다(약 30초 유휴 + 5초 확인 대기 + 쓰기 막힘 확인 구간). ADR 0004의 "쓰기 막힘에서도 장애를 감지한다"는 기대와 일치한다.
- 이 실행에서 서버 RSS 증가는 1~2MB에 그쳤다. 시나리오가 미완료 요청을 32개(본문 64KiB, 약 2MiB)로 묶어 밀어 넣기 때문에 서버의 쓰기 대기열 상한(64MiB)에는 닿지 않는다. 대기열 상한 근처의 메모리를 보려면 `--inflight`와 `--body-bytes`를 키워 따로 재야 한다.
- 유휴 PING을 0으로 끈 설정은 읽기 멈춤만으로 끊기지 않는다(ADR 0004에 적힌 한계). 하네스는 이때 `--max-wait` 안에 감지하지 못하면 실패로 끝낸다.

### TLS 동등성

양쪽 서버에 TLS 1.3과 같은 암호 스위트를 강제했고(자식 JVM `jdk.tls.*`), 실제 부하 전에 협상 결과를 기록한다. 시험에서 nio·netty 모두 `TLSv1.3` / `TLS_AES_128_GCM_SHA256`으로 협상됐다. 평문은 하네스 한정 대조군이며 제품 설정으로 노출되지 않는다(ADR 0004: 운영 경로는 채널 보안 필수).

### netty TCP와 WebSocket 비교

`matrix --transports netty-tcp,netty-ws`로 같은 netty 서버·netty 클라이언트에서 바인딩만 바꿔 같은 JSON 스키마의 결과를 낸다(ADR 0007). 스키마가 같음은 시험으로 확인했다. WebSocket 프레이밍 비용의 크기는 전용 머신 측정 뒤에 해석한다.

## 다음에 할 일

1. 전용(또는 코어를 나눈) 머신에서 기본 설정으로 핵심 행렬을 다시 잰다: 서버와 부하 생성기를 `taskset`으로 다른 코어에 고정하고 `loadgenBottleneck`이 false인 실행만 쓴다.
2. 단일 스케줄러 스레드의 한계(높은 도착률·연결 100 이상)가 계속 부하 생성기 병목으로 표시되면, 부하 생성기를 여러 스레드로 나누는 개선을 이 하네스에 더한다.
3. 필요하면 확장 행렬(연결 1,000, 64KiB, 평문 대조군)과 soak(기본 1시간, 선택 8시간)을 돌린다. soak는 이번에 짧은 시험만 돌렸다.
4. 절대 합격선(허용 p99, 메모리 상한)은 실사용 조건이 정해진 뒤 정하고, 그 기준으로 제품화 여부를 판단한다([Netty 도입 적합성](netty-adoption.md) "도입 전 검증" 4번).

## 한계

- 이 문서의 처리량 표는 단축 설정 1회 실행이다. 반복 범위가 넓어 작은 차이는 해석하지 않는다.
- netty는 자체 이벤트 루프를 가진 독립 실행만 쟀다. 이미 netty를 쓰는 호스트에 삽입하는 경우는 범위 밖이다.
- Netty 네이티브 전송(epoll 등)과 JDK 8·17 런타임, 별도 머신을 쓰는 분산 측정은 후순위다.
