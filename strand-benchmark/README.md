# strand-benchmark

`strand-core` 내부 비용의 증가율을 재는 JMH 벤치마크. 배포하지 않는다. #200에서 만들었다.

판정은 절대 시간이 아니라 증가율로 한다. 결과는 시간 단위(`AverageTime`, ms/op)이고 작을수록 좋다. 입력(바이트 수, 요청 수)이 커질 때 시간도 그만큼(선형)만 늘어야 한다. 대기 수를 100배(2000→200000) 키웠을 때의 변화로 판정한다. 이전 이슈(#216)의 처리량(ops/ms) 수치는 `1/x`로 ms/op로 환산해 비교한다. 유휴 PING 송신 경로는 연결당 30초에 한 번이라 재지 않는다. CI는 컴파일(`jmhClasses`)만 확인하고 측정하지 않는다. 러너의 수치는 잡음이 커서 근거로 쓸 수 없다.

`Frames` 같은 패키지 전용 클래스를 쓰려고 벤치마크 소스도 `io.github.ppzxc.strand.core.internal` 패키지에 둔다. 클래스패스로 실행하고 `module-info`가 없어서 가능하다.

## 실행

```sh
./gradlew :strand-benchmark:jmh                              # 전체
./gradlew :strand-benchmark:jmh -PjmhIncludes=OutboxBenchmark   # 정규식으로 일부만
```

결과는 `strand-benchmark/build/results/jmh/results.json`에 남는다.

| 벤치마크 | 보는 것 |
|---|---|
| `ReceiveManySmallFramesBenchmark` | 청크 하나에 작은 프레임이 가득 찬 입력의 `receive()` |
| `ReceiveBigFrameBenchmark` | 큰 프레임 하나가 작은 조각으로 도착하는 입력의 `receive()` |
| `ReceiveRequestFramesBenchmark` | 실제 요청 프레임 1024개(본문 64B/1KiB/64KiB)를 서버가 받는 비용. 호출 하나가 서버 256/16/1대를 받으므로(호출당 측정 시간 확보, #429) 서버 한 대 비용은 결과를 그 수로 나눈다. 파싱과 `REQUEST_RECEIVED` 이벤트 생성 포함. 위 두 Receive 벤치마크의 예약 프레임이 대조군이다 |
| `ReceivePingBenchmark` | PING 1000/10000/100000개를 받고 ACK를 쌓는 비용 |
| `OutboxBenchmark` | 오류로 닫기, 번호표 취소, 번호표 상태 조회, 기한 확인의 쓰기 대기열 비용 |
| `TicketLookupBenchmark` | 번호 없는 대기열 요청, 번호 받은 쓰기 전 요청, 쓰기 시작한 요청을 번호표로 상태 조회, 취소 후 재충전하는 비용. 대기 수 2000/20000/200000에서 퍼뜨린 표본과 이웃 표본을 비교한다. 대기 수와 무관해야 한다(#207) |
| `RespondBenchmark` | 서버가 받아 둔 요청 전부에 `respond`하는 비용. 대기 수 2000/20000/200000 × 응답 순서(먼저/나중 보낸 것부터). 응답 한 건당 비용이 대기 수와 무관해야 하므로, 한 호출이 n건 전부를 처리하는 시간은 대기 수에 선형이어야 한다 |
| `ResponseConsumeBenchmark` | 클라이언트가 응답 전부를 받아 내 요청 장부에서 소비하는 비용(`RESULT` 이벤트). 같은 대기 수·응답 순서 행렬. 응답 한 건당 번호표 조회가 대기 수와 무관해야 하므로(#207) 전체 시간은 대기 수에 선형이어야 한다 |
| `WriteCompletionBenchmark` | 프레임 하나를 다 쓰는 비용이 응답을 기다리는 열린 요청 수(100/2000/20000)에 비례하지 않는지(#382) |
| `DeadlineExpiryBenchmark` | 기한 있는 대기 요청이 많을 때 `advance`의 비용. 만료 수(10/100/1000)에만 비례하고 대기 수와 무관해야 한다(#207) |

## 시나리오와 측정 경계

공통 준비 도우미는 벤치마크 엔드포인트를 서문·HELLO·AUTH 관문까지 수립하고, 송신 진행과 이벤트를 비운다. 벤치마크는 진행 보고 방식으로 입력을 한도 있게 넣고 출력은 통로가 받아 준 만큼 완료로 보고한다. `Level.Invocation` 설정과 정리 시간은 JMH 측정 밖이다. 준비·정리 경로는 작은 자체 검사로 입력 조건과 기대 이벤트·출력 개수를 확인한다. 예약 제어 프레임은 확장 검사만 하고 무시되므로 이벤트나 응답을 만들지 않는다.

| 벤치마크 | 입력과 비교 조건 |
|---|---|
| `ReceiveManySmallFramesBenchmark` | 20바이트 예약 프레임으로 채운 128KiB, 1MiB, 8MiB 청크 하나를 받는다. 이벤트와 출력이 비어 있어 프레임당 처리 증가율만 본다. |
| `ReceiveBigFrameBenchmark` | 32KiB, 128KiB, 1MiB 예약 프레임을 1KiB 조각으로 나눠 받는다. |
| `ReceiveRequestFramesBenchmark` | 1,024개 실제 요청 프레임을 64B, 1KiB, 64KiB 본문으로 받는다. 호출당 총 본문을 16MiB로 맞추려고 각각 256, 16, 1개 서버를 처리한다. 결과를 서버 수로 나눠 서버 한 대의 비용을 비교한다. |
| `ReceivePingBenchmark` | 1,000, 10,000, 100,000개의 PING을 받아 같은 수의 ACK가 쌓이는지 확인한다. 주기적 유휴 PING 송신 비용은 포함하지 않는다. |
| `OutboxBenchmark` | 2,000·20,000개 요청으로 같은 시작 상태를 만든다. 닫기, 번호표를 오래된 것부터/최신부터 취소, 모든 상태 조회, 기한을 넘기지 않는 시계 진행을 잰다. 양 끝 취소 순서로 번호표 탐색의 최선·최악을 비교한다. |
| `TicketLookupBenchmark` | 대기 수 2,000·20,000·200,000, 상태(번호 전·번호를 받았으나 쓰기 전·쓰기 시작), 표본 분포(전체에 분산·이웃)를 조합해 1,000개 번호표를 찾는다. 취소 측정은 각 취소 직후 새 요청으로 대기 수를 복구하며, 시간에는 취소와 새 요청이 모두 들어간다. |
| `RespondBenchmark`, `ResponseConsumeBenchmark` | 대기 수 2,000·20,000·200,000과 응답 순서(요청 순서·역순)를 조합한다. 매 호출의 준비는 측정 밖이고, 한 건당 비용이 대기 수와 무관한지 본다. |
| `WriteCompletionBenchmark` | 응답 대기 요청을 100·2,000·20,000개 열어 둔다. 각 호출에서 200개 요청을 쓰고 취소해 400개 프레임(요청과 RESET)을 처리한다. |
| `DeadlineExpiryBenchmark` | 만료되지 않는 쓰기 전 대기 요청을 깔아 두고, 만료 0회 진행 또는 기한 1ms인 10·100·1,000개를 만료한다. 번호 없는 요청과 번호를 받은 요청을 각각 측정하며 예상 결과 사건 수를 확인한다. |

JMH 점은 비용 증가율을 위한 비교다. 입력 크기에 따른 기울기를 읽고, 절대 처리량·실제 전송 성능이나 장기 부하 결과로 해석하지 않는다.
